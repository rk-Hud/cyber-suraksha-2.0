# Account service operations

CYBER SURAKSHA 2.0 is independently architected, developed, authored and owned by Jatoth Ramakrishna. This guide covers the GitHub Pages interface and Neon account API. Earlier Render instructions do not configure this API.

## Deployment boundaries

GitHub Pages publishes only the output generated by `web/pages/scripts/export_site.py`. Set the public API URL in `web/pages/source/site.json`; it is an address, never a credential. The Node.js 24 Function `csportalapi` runs next to the existing Neon database; Neon injects the branch-specific `DATABASE_URL` privately.

The API retains the `portal_*` schema, account identifiers, Werkzeug password hashes, case histories and encrypted owner authenticator seed. Test fixtures never replace production records. Existing Render services stay available until replacement sign-in, real email delivery, owner MFA and private cases are verified.

## Private configuration

Configure these values in the Function environment. Never put their values into issues, documents, public files or conversations.

| Variable | Purpose |
| --- | --- |
| `API_SESSION_KEY` | Random secret, at least 32 characters, for API session tokens |
| `API_OTP_KEY` | Different random secret, at least 32 characters, for email codes |
| `TOTP_ENCRYPTION_KEY` | Exact existing private value from the owner Render service; changing it prevents decryption of the enrolled owner factor |
| `ADMIN_EMAIL` | Configured owner email; owner role checks also apply |
| `ALLOWED_ORIGINS` | `https://rk-hud.github.io`, without a path or wildcard |
| `PUBLIC_WEB_URL` | `https://rk-hud.github.io/cyber-suraksha-2.0/` |
| `MAIL_PROVIDER` | `resend` for the selected provider |
| `MAIL_FROM` | Mailbox at a verified sending domain controlled by the owner |
| `RESEND_API_KEY` | Existing sending key, copied privately |
| `EMAIL_READY` | Set to `1` after the sender and key are configured |
| `REGISTRATION_ENABLED` | Keep `0` during setup; set `1` after delivery and owner MFA work |
| `NODE_ENV` | `production` |

GitHub Pages is a website URL, not an email-sending domain. Resend verification requires DNS records under a registered domain whose DNS the owner controls. A shared testing sender cannot deliver production OTPs to arbitrary citizens.

Copy the existing authenticator encryption key privately without changing its bytes. Do not clear the enrolled factor or remove MFA to bypass a missing key. Existing Render sessions do not become API bearer sessions; sign in again after migration.

## Activation checks

1. Check API health. Capability flags report configuration; they do not prove inbox delivery.
2. Configure a verified sender, the existing sending key and original authenticator encryption key. Verify owner password/email-OTP sign-in and a current authenticator code, without publishing codes or tokens.
3. Turn on registration and test with a consenting mailbox. Verify delivery, expiry, wrong-code rejection and successful sign-in.
4. Submit a fictional case. Check a second account cannot access it. Update it as owner and confirm the citizen sees the timeline and receives a generic status email.
5. Verify password recovery, session revocation, disabled-account behavior and MFA expiry. Record outcomes without personal details.
6. Keep a private restore point and rollback access before removing the two obsolete Render services.

Case updates use a durable notification outbox. Automatic attempts follow committed case changes; failed jobs stay queued for retry. The owner dashboard has a protected retry action. Provider acceptance does not guarantee inbox delivery; there is no continuously running mail worker.

## Privacy and authorization

The checker and planner never send input to this API. Account and support forms deliberately submit their fields over HTTPS. Tokens stay in page memory; reloading or changing language requires another sign-in. Account and case records stay in PostgreSQL, not browser storage or static files.

Case endpoints require bearer authentication and record ownership. Sensitive owner actions require the configured role and email plus recent authenticator verification. Validated content edits render as text; arbitrary executable website changes remain a repository/deployment operation. No document uploads are accepted.

Do not solicit passwords, OTPs, PINs, full account numbers or identity documents. Handle deletion requests privately with a recorded retention decision. Never export personal records to the public repository.

GitHub Pages cannot set arbitrary response headers. Generated HTML uses a CSP meta tag; API responses set their own CSP, HSTS, anti-framing and no-store headers. Origin checks supplement bearer authorization.

Run `.github/workflows/account-services.yml` for the exact revision. Build the API bundle with `npm run build` and deploy it to the intended Neon branch. Do not copy another branch's database URL into a deployment.

Publish generated `web/pages/docs/` to `gh-pages` under `/docs`. Preserve the project base path and verify all three language/account pages and assets. Roll back the Function deployment if needed; never overwrite production with an isolated test database.
